# Reviewed application dependency evolution

Date: 2026-10-21. Scope: the existing application graph in commit `a865777`, not a dependency installation or milestone promotion.

## Decision and historical boundary

REQ-FND-03 permits the selected baseline or a reviewed replacement. The M0 prototype and `provenance.json` remain unchanged historical evidence. The application now has four explicit direct-dependency differences: `@aws-sdk/client-s3` is added at `3.1141.0`, Next is pinned at `16.3.8` instead of `16.3.6` to retain the existing tested application patch, `react-admin` is removed because the delivered template administration surface is now project-owned shadcn/ui-style source, and Nodemailer `10.2.1` is added for the optional customer-configured SMTP transport. SMTP stays disabled by default; the dependency adds no provider credentials or delivery until a buyer explicitly configures the encrypted server-side SMTP setting. Adoption history alone is not compatibility proof; current frozen-lock, typecheck, build and dependency-audit results must accompany this decision.

`tooling/root-dependency-baseline.json` records the exact accepted application lock and these four transitions. The application lock also contains its already-existing transitive overrides; this decision preserves their exact bytes rather than claiming that the whole graph differs only by direct package changes. The root checker supports explicit reviewed addition and removal transitions; it does not treat an added or missing dependency as accidental drift.

The root checker reconstructs the complete expected dependency map from the pinned prototype plus these transitions, rejects alternative dependency sections and package-manager drift, verifies both lockfiles byte for byte, and retains workspace/TypeScript/Docker isolation checks. The complete `pnpm-workspace.yaml` configuration is also pinned, including its existing transitive overrides and lifecycle-build allowlist; package extensions or changed overrides cannot bypass the guard. Historical JSON and workspace text hashes normalize CRLF to LF only so Windows and Linux checkouts identify the same text. Content changes still fail. Lock hashes never normalize line endings.

Editing either invalidates development evidence. Root-integrity regressions cover the accepted graph, dependency additions/removals/versions/ranges, package-manager drift, historical tampering, raw lock drift, checkout line endings and legacy isolation. Future graph changes require a new rationale, current frozen-lock/typecheck/build/audit evidence and independent review.
