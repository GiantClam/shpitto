## 一、验收机制与推进规则

1. 设置 M0–M8 共九个阶段，复用现有任务 `1.8`、`2.8`、`3.12`、`4.12`、`5.10`、`6.10`、`7.14`、`8.15`、`9.15` 作为阶段验收节点。实施任务仍为 **105 项**。任务勾选完成与阶段验收通过是两类独立记录。
2. 每个已实施任务仍须满足原有 SC/T 场景和证据要求。本文件负责汇总阶段通过条件，列出的最低检查项不替代其他必测场景。较早阶段的某一验证配置通过，不能代表后续配置或整个 G 验收项通过。
3. 实施负责人提交证据，由另一位审核者检查，集成负责人记录技术结论及允许开始的后续任务。产品负责人接收阶段报告，并负责商业政策和发布决策。在已授权的工作范围内，技术验收 `PASS` 后可继续符合前置条件的工作，无须为每个常规步骤再次询问用户。这不构成付费、生产环境变更或公开发布的授权。
4. 阶段 `FAIL` 或 `BLOCKED` 时，阻止依赖它的任务及相应发布声明。独立任务仅在自身明确前置条件已通过、且不修改已冻结的共享契约时，才可继续。M3 通过后，M4 与 M5 可以并行；其中一个阶段通过不能解锁 M6 的最终验收。M7 部分文档和 Skill 初稿可在 M1 后按具体任务依赖提前开展，但 M7 最终验收须等待 M6。
5. 已通过的阶段只对记录中的源代码、数据库结构、依赖、配置、政策摘要及证据环境有效。相关文件或契约变化后，受影响证据标记为 `STALE`；审核者须记录影响并重跑受影响场景与回归检查。认证、账本、状态机等横切契约变化还会重新打开依赖阶段。保留旧证据必须说明等价性，仅引用旧提交标签不足以证明有效。
6. 验收门禁的自动检查属于后续任务 `1.7`、`2.3` 及最终打包任务 `9.14`、`9.15` 的实施交付物。目前的 JSON/Markdown 文件只规定机制，不能描述为已安装并生效的 CI 验收系统。

## 二、所有阶段共同适用的通过标准

| 维度 | 必须达到的结果 |
| --- | --- |
| 范围与场景 | 当前阶段要求的全部任务、当前验证配置下的全部必测场景完成，且 **100% 通过**。跳过、原因不明的偶发失败、缺少结果和阻塞均不能算通过。 |
| 构建与检查 | 已实施的新应用范围内，冻结锁文件安装、相关构建、类型检查、Lint、导入边界检查全部成功退出。警告须登记，且不能掩盖必过项失败。旧项目不参与新项目检查。M0 检查一次性原型，不要求尚未实施的新应用提前构建。 |
| 覆盖率 | 已交付、自有核心领域模块的汇总分支覆盖率至少 **80%**，审核前明确分母，以及生成代码、第三方代码的排除规则。金额、授权、租户隔离、幂等及状态转换的全部必测场景，不受覆盖率数字影响，必须逐项通过。尚未交付领域行为的 M0/M1 记为“尚不适用”，不能记为 100%。 |
| 缺陷 | **未关闭的 P0/P1 为零**。任何必过条件失败均阻止验收，不能通过降低缺陷级别绕过。确实不属于强制验收条件的 P2/P3，只有经独立审核、记录影响、负责人和到期日后才可保留；这类记录不能豁免测试、安全、资金或数据丢失标准。 |
| 隔离与安全 | 所有反向授权场景通过；不能泄露其他工作区的数据或对象 URL，不能在浏览器、导出包或日志暴露密钥，不能执行未经验证的特权操作，也不能绕过领域命令直接执行受保护的通用 CRUD。 |
| 资金与任务完整性 | 不出现负的可消费余额、重复发放/扣费/退款、未授权资金变更、审计事务丢失、盲目重复付费提交，或已终结结果被重新打开。必须提供数据库不变量证据，单凭截图不够。 |
| 界面完整性 | 相关成功、加载、空数据、错误、无权限状态正常。适用的产品和后台流程在桌面 **1440×900**、移动端 **390×844** 下审核，并检查当前阶段控件的键盘可操作性。被阻止的操作须给出可执行的下一步提示。这两个尺寸是验收视口，不代表所有浏览器、设备已经认证。 |
| 证据 | 记录准确候选版本、环境与工具版本、配置限制、夹具/随机种子、命令、预期与实际结果、日志/断言及审核结论；不得包含密钥。外部失败须区分上游责任和应用责任。 |
| 恢复能力 | 实施阶段要求的故障与恢复演练实际成功，不破坏无关工作、不重复产生资金效果。相应能力进入实施阶段后，仅有回滚说明不够。 |

**缺陷级别定义：**

- **P0：** 正在发生的数据或凭据暴露、不可恢复的数据丢失、未授权资金效果，或大面积不可用。
- **P1：** 已承诺的核心旅程，或必须具备的完整性、恢复能力失效。
- **P2/P3：** 其余影响有限或非关键缺陷。级别名称不能覆盖“必测场景必须通过”的规则。

### 可重复性检查规范

以下是本次选定的工程验证默认值，不是生产容量或供应商 SLA 承诺。

1. 对选定的每个关键数据库竞态，在真实 PostgreSQL 上至少进行 **3 次独立重置后的重复验证**，记录执行交错顺序或随机种子。超额消费、重复命令/Checkout 竞争、所有权修改等适用场景使用 **10 个同时发起的操作**，断言准确最终状态及外部调用意图数量。
2. 同一资金或回调事件重放 **20 次**，再加入冲突载荷及乱序排列，验证只产生一次预期效果、冲突处理正确且无关记录不变。使用确定性本地夹具或沙箱事件；不得为了凑次数重复产生付费调用。
3. 对每个已记录的崩溃边界，分别停止并重启进程一次，比较任务、发放、账本及 outbox 状态。边界包括额度预留、领取派发权、外部响应不确定、已验证的 inbox 接收、对象已上传但数据库尚未终结，以及外部成功但本地尚未确认。
4. 通过受控的应用/数据库时钟验证到期或截止时间的“之前、恰好到达、之后”，并在契约检查中使用真实持久化的生产间隔配置。加速的夹具时钟必须标注，不能声称已完成实际持续一小时的服务试运行。
5. 每次失败都应保留并修复，不能反复重跑直到偶然成功后抹去失败记录。每个供应商/模式组合至少取得 **1 个真实可用输出**，使用已授权账户与预算；如果证据暴露不稳定性，应选择更充分的样本。

## 三、M0–M8 阶段验收

各阶段列出的 G 编号表示该阶段为相应验收项提供支持证据。整个发布验收闭环仍须完成第四节及 M8 要求的全部适用环境和验证配置。

每条阶段标准按 `<阶段>-C<两位条目序号>` 记录，例如 `M0-C01`。M8 的编号跨三个子检查点连续排列：RC 对应 `M8-C01–M8-C05`，BETA 对应 `M8-C06–M8-C08`，STABLE 对应 `M8-C09–M8-C11`。合计 **49 条阶段汇总标准**；共同标准及原有必测 SC/T 场景同时适用，不能被汇总条目替代。

### M0：可行性与保全方案验收（任务 1.8）

| 项目 | 要求 |
| --- | --- |
| 准入条件 | 范围、设计及执行计划的权限已明确；任务 `1.1–1.7` 完成。 |
| 提交负责人 | 基础工程负责人。 |
| 独立审核者 | 架构/发布审核者。 |
| 验证环境 | 仓库只读盘点，以及采用已选技术栈的一次性原型。 |

**必过标准：**

1. 每个顶层路径均已分类为迁移、保留、私有或可重新生成。全部已跟踪文件，以及选定的未跟踪/被忽略但由人员编写的文件，均有目标或保留位置、哈希及恢复说明。不存在未解决的覆盖冲突或目标路径越界冲突。`.git`、当前 OpenSpec 及已批准规划源文件均有明确保留规则。
2. 已选技术栈可在冻结锁文件下解析并完成原型构建，不依赖不受支持的 peer dependency 覆盖。所有复制的源码、组件、二进制均有来源与允许再分发的证据；许可不明确的组件不得使用。
3. 原型打通 Better Auth → 独立运营权限 → React-admin → 领域命令 → Drizzle。注入领域/账本/审计/outbox 失败时，命令事务完整回滚；未经授权的直接 API 请求失败。证明只有一个数据库迁移权威来源。
4. 带版本的 MDX/静态搜索、后台隔离、独立运行打包、工作进程媒体探测，均在各自原型范围内构建或运行成功。媒体工具的校验值与许可证说明已记录。
5. 外部接口契约与账户矩阵明确。尚未取得的真实模型、账户或付费证据分配到 M4/M6/M8；除非它们已证明某个选定的必需契约不可实现，否则不能因此直接判 M0 失败。E01–E05、共享 DTO、领域锁顺序和数据库结构的责任归属冻结。

**提交证据：** 盘点与迁移/恢复映射、锁文件与来源报告、原型命令及断言日志、外部输入登记；T44 盘点子集、T52、T59–T62 原型子集；SC-FND-01/02/06/07/11/12/13/14。

**通过后允许：** 开始 M1 保全快照与迁移。此时不将 G02/G15/G31 标记为整体通过，也不停止任何线上服务。

### M2：身份、租户隔离与积分不变量验收（任务 3.12）

**通过后允许：** 进入 M3。G05 的浏览器旅程等待任务 `4.13`/M3；Stripe 发放、真实任务与供应商结算等待相应后续阶段。

### M3：持久化本地产品与恢复能力验收（任务 4.12）

| 项目 | 要求 |
| --- | --- |
| 准入条件 | M2 `PASS`；任务 `4.1–4.11` **以及 `4.13`** 完成。 |
| 提交负责人 | 产品/领域负责人。 |
| 独立审核者 | 验证/产品审核者。 |
| 验证环境 | 干净本地安装、PostgreSQL、持久化 Mock/工作进程/存储、浏览器。 |

**必过标准：**

1. 无云凭据时，新用户能够登录、使用工作区、看到服务端报价、生成可播放的 Mock 视频、查到历史和积分来源，并下载归属于该工作区的资源。应用及工作进程重启后记录与输出仍保留。
2. 所有者与成员在界面上可完成其权限允许的团队创建、邀请/接受、成员移除、所有者转移和工作区切换。撤销访问及个人工作区禁止的操作在 API 和浏览器检查中均失败。必要状态和验收视口通过。

4. 每个相关本地崩溃边界、独立扫描/租约 fencing、调度丢失、队列饥饿、截止时间与成功竞态都保持不变量。提交结果未知时，在有限边界内失败并退还积分，不产生另一次付费提交意图；迟到的成功输出保持隔离。
5. 输入/输出 MIME、大小、路径、媒体及私有下载检查拒绝不安全或跨租户内容。通过确定性夹具验证 SSRF/重定向防护；不宣传公共 API Key 产品接口。

**提交证据：** J1/J3/J4/J7 本地演示；T01–T20 相关集成场景、T49/T53 本地恢复、`4.13` 界面场景；SC-GEN/CRD/IAM 结果及重启/崩溃断言。

**通过后允许：** 在冻结共享契约的前提下并行开展 M4/M5。Mock 证据不能使 G03/G10 通过。

| `NOT_STARTED` | 尚无该阶段实施证据。 |
| `IN_PROGRESS` | 正在实施或收集证据；不能解锁依赖它的验收节点。 |
| `READY_FOR_REVIEW` | 提交者认为必测场景已完成且证据可获取，但审核者尚未判定通过。 |
| `PASS` | 独立审核与集成负责人确认：该准确候选版本/验证配置的全部必过条件满足。 |
| `FAIL` | 必测场景或完整性条件失败；修复后，重跑受影响场景及回归证据，再提交审核。 |
| `BLOCKED` | 必需账户、预算、权限、环境或证据不可用；标明负责人和下一步，不用 Mock 冒充。 |
| `STALE` | 曾通过的证据已不匹配相关源码、配置、数据库结构或政策，须影响审核及重新验证。 |

M8 的三个子检查点分别记录。只有 STABLE `PASS` 后，M8 主状态才变为 `PASS`。获得授权的付费 Beta 可以在 BETA `PASS` 后开展，此时 M8 仍保持 `IN_PROGRESS`。

### 5.3 每次验收报告的固定内容

1. 本阶段交付范围。
2. 需求与场景覆盖情况。
3. 可运行演示。
4. 实际观察到的证据。
5. 阻塞/缺陷及建议纠正措施。
6. 回滚位置。
7. 准确验收结论，以及下一步允许开展的任务。

技术审核须独立于受影响的实施工作。若人员安排导致某一人工检查只能由实施者执行，另一名审核者仍必须检查其记录后才能判 `PASS`。第二个自动化代理可以提供这种技术审核，但不能代替产品负责人作商业授权。

### 5.4 失败处理流程

保留原失败证据 → 分类并指定负责人 → 停止依赖工作 → 在负责该问题的契约/领域层修复 → 重跑失败场景及受影响回归 → 更新摘要和下游影响 → 独立复审。

不得跳过必测项、通过重命名缺陷绕过验收，也不得为恢复当前阶段而回滚无关的客户工作。
