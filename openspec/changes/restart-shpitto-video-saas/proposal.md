# Restart Shpitto as an AI video SaaS source template

## Why

The current repository is a website-generation platform. The confirmed product sells developers a clean, independently deployable AI video SaaS template. Retrofitting the old runtime would retain unrelated orchestration, deployment and ownership assumptions. A preserved legacy archive and new root application make customer delivery, business rules and support boundaries explicit.

The reviewed input has D01-D31, ten journeys, 31 acceptance gates and 62 scenario families. This change converts them into observable requirements and dependency-gated tasks, closing missing race, recovery and policy boundaries. It does not claim the software has been built.

## What Changes

- Preserve legacy source, Git history and selected local authored state; build the new product at the root and exclude legacy from new tooling/export.
- Provide persistent local operation, identity/teams, transactional credits, Replicate/fal.ai video, Stripe subscriptions/packs, operations and optional FirstPromoter integration.
- Reuse the selected frameworks; retain domain-owned financial/authorization rules and one database authority.
- Ship twelve external-agent Skills, governed brand/page/site customization, and release-matched developer Docs/buyer guides.
- Deliver clean customer repositories/version archives, two deployment paths and update/support entitlements through a separate vendor surface.
- **BREAKING:** replace root application/workspace/build/deploy contracts after preservation and M0 evidence. Source relocation does not implicitly decommission online services.

## Capabilities

Implementation acceptance follows the [M0–M8 staged contract](acceptance-gates.md). Existing gate tasks retain their IDs; M8 separates RC, paid-Beta and stable readiness. All stage records remain NOT_STARTED until observed implementation evidence is independently reviewed.

### New Capabilities

- `restart-foundation`: preservation, stack validation, root isolation and persistent local prerequisites.
- `identity-workspaces`: authentication, minimal membership, tenant authorization and suspension boundaries.
- `credit-accounting`: grants, reservations, expiry, immutable lineage and failure compensation.
- `generation-lifecycle`: submission, cancellation, bounded recovery, delivery and terminal outcomes.
- `provider-integrations`: normalized Mock/Replicate/fal contracts and four real generation paths.
- `billing`: checkout, canonical payment reconciliation, grants and cash recovery.
- `operator-administration`: separate roles, authorized commands, audit and recovery visibility.
- `affiliate-programs`: optional independent program, stable workspace attribution and reviewed payout handoff.
- `governed-skills`: twelve workflows, protected contracts and trusted evidence-bound customization.
- `developer-documentation`: versioned template, Skills and actual API/integration documentation.
- `deployment-release`: clean export, independent install, managed/Docker operation and evidence.
- `template-commerce`: separate source sales, customer access and twelve-month update/support policy.

### Modified Capabilities

None. There is no existing OpenSpec baseline. Legacy source is preserved rather than represented as an already migrated capability.

## Impact

Future work affects root manifests, `src/`, `trigger/`, `scripts/`, `deploy/`, `skills/`, `.shpitto/`, `content/docs/`, buyer docs, `vendor/sales/` and `legacy/shpitto-platform/`. It introduces buyer-owned service configuration and reviewed migrations. Exports exclude vendor business, legacy, private state, old history and secrets.

Public generation API/customer keys, embedded coding agents, general website building, an in-app visual editor, custom commission accounting, annual billing and automatic mid-cycle plan changes are outside V1. Prices, commission rates, account qualification and budgets are phase inputs, not invented values.

Execution: M0 → M1 → M2 → M3 → parallel M4/M5 → M6 → M7 integration → M8. Docs/Skills preparation can begin after M1. Apply work requires implementation authorization and the relevant entry gate; external actions retain their own authorization boundaries.
