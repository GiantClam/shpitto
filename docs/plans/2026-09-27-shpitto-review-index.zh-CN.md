## 2. 审核时如何理解文档状态

| 状态 | 含义 | 审核方式 |
| --- | --- | --- |
| 已确认需求 | grill-me 需求澄清中已经确认的 D01–D29，以及后续 D30 开发者文档中心和 D31 开源优先原则。具体后台框架已由本次工程方案选定，区别于原始需求确认。 | 核对记录是否准确，有误时直接指出对应 D 编号并提出修订。 |
| 建议实现方案 | 为满足已确认需求提出的架构、数据结构、流程、默认权限、工具和保护机制。 | 判断方案是否合理、复杂度是否合适、边界是否清楚；可以替换实现方式。 |
| 待决策事项 | 实际账号及预算、商业价格、佣金比例、源码许可条款等；技术栈、具体模型和部署参考路径已选定。 | 按实施计划第 13 节给出的阶段截止点解决，不把建议值当成已确认政策。 |
| 已完成的文档评审 | 原 D01–D29 计划已通过架构师复审与独立评审，正文保留该历史记录；D30 和 D31 属于后续补充。 | 历史通过记录不自动覆盖新增内容，也不代表建议默认值全部获得批准或软件验证通过。 |
| 后续验收要求 | 实施后需要取得的可核对结果和证据。 | G/T 编号是未来验收与测试设计；没有实际执行记录的项目不能记作通过。 |

例如：Replicate 与 fal.ai 的四个模型端点已经选定，买家 SaaS 联盟选定 FirstPromoter V2；源码销售选择 Lemon Squeezy。真实账号资格、实测费用、佣金比例及商业等待期仍须在发布前落实，不能把这些外部输入与技术选型混淆。

## 5. 已确定的技术与剩余发布输入

| 范围 | 已选方案 |
| --- | --- |
| Web 与数据 | Node 24 LTS、Next.js 16.3.6、React 19.3.0、TypeScript 6.0.3、PostgreSQL 17、Drizzle、Better Auth。 |
| 运营与产品 UI | React-admin OSS 5.15.4；产品页面采用 shadcn/ui + Tailwind；不引入 Payload 或 Refine 运行时。 |
| 开发者 Docs | Fumadocs + MDX，公开版本化文档、静态搜索、共享正文及买家导出。 |
| 视频 | Replicate 与 fal.ai 的四个 Wan 2.2 文生／图生端点，明确结构版本、参数及回调验证。 |
| 支付与联盟 | Stripe Hosted Checkout／Portal；FirstPromoter V2 API，稳定工作区身份、原生默认首单计佣及运营审核付款流程。 |
| 生产部署 | Vercel + Neon PostgreSQL 17 + 私有 R2 + Trigger.dev Cloud + Resend；Docker 应用使用相同外部契约；保留 SMTP 适配。 |
| 本地体验 | Docker PostgreSQL、本地持久化任务 worker、文件存储、邮件捕获和 Mock 生成。 |

**已经选定不等于已经验证。** 依赖锁解析、构建、迁移、真实 API 和部署证据属于后续实施验收；不能再将这些验证工作写成框架或服务尚未选定。
## 6. 如何提交审核意见

本轮详细技术方案已依次通过 Architect 复审及独立 Critic 审查。三项修订是付款／退款统一核对、任务恢复扫描与租约校验、持久化联盟审核。完整证据见[本轮评审记录](../../.omx/plans/shpitto-detailed-design-review.md)。

可以直接使用编号反馈，不必重写整份文档：

- `Dxx`：修改产品范围或已经记录的需求。
- `Jx`：修改用户流程。
- `Mx`：修改实施顺序、交付阶段或依赖。
- `Gxx`：修改验收门槛。
- `Txx`：补充或修订具体测试场景。
- `计划第 x 节`：修改架构、技术方案、建议默认值或商业待决策事项。
