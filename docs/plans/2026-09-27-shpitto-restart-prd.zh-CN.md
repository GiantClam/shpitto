## 2. 产品与客户

Shpitto 向开发者销售可独立部署的 AI 视频 SaaS 源码。买家使用自己的基础设施、模型供应商账号、支付账号，以及可选的联盟账号，运营自有品牌的视频服务。初期产品体验和文档面向使用英语的海外买家。

这里包含两套独立业务：

1. **Shpitto 模板销售业务：**包含开发者文档页面的轻量销售网站、通过现有渠道完成源码许可购买与交付、独立联盟推广，以及客户更新和支持服务。
2. **买家运营的视频 SaaS：**拥有自己的营销网站、身份认证、个人和团队工作区、付费订阅与积分包、视频生成、资产管理、管理后台，以及可选择启用的联盟推广。

源码模板销售订单不得被当作视频服务的积分购买订单。交付给客户的模板不得包含 Shpitto 销售方的运营资料、凭据、旧项目历史或旧应用。

## 4. V1 用户流程

### J1：取得并运行模板

买家收到干净的私有仓库邀请或带版本号的发布包，按照文档说明，通过 Node/pnpm/Docker 路径，在无需云服务凭据的情况下，完成本地持久化登录、创建工作区、执行一次 Mock 生成、保存生成资产，并查看积分历史。演示模式必须明确标识，不能被用来冒充真实支付或真实供应商集成的验证记录。

### J2：个性化定制买家的 AI SaaS 网站

通过外部编码 Agent 的 Skills 完成品牌定制、新建页面、指定页面修改或整站一致性改版。Skill 应检查基线、对请求进行分类、声明修改范围、组合使用已批准的资源、检查实际差异，并报告验证结果与恢复信息。个性化修改必须保留真实的身份认证、支付和生成行为。涉及受保护业务契约的请求，应进入对应的专用工程变更或扩展流程。

### J3：生成视频

用户在有权限使用的工作区内，选择受支持的供应商与生成模式，填写经过校验的模型参数，查看本次生成所需积分，再提交任务。积分预占必须以原子操作完成。任务通过持久化的执行生命周期推进；成功生成的输出必须先复制到工作区控制的存储中，之后才能标记为已交付。有权限的用户可通过限定访问范围的方式下载结果。Replicate 和 fal.ai 都必须提供真实的文生视频、图生视频验证记录。

### J4：取消或恢复任务

用户只能在开始向供应商派发请求之前取消任务。取消成功后释放已预占的积分。对于失败且没有交付可用视频的任务，必须全额退还本次生成积分。提交结果不确定时，应先核对和恢复状态，不能盲目重新提交。供应商收费属于运营方成本记录，与客户积分处理结果分开记录。

架构还必须处理始终无法追踪结果的提交。每个模型都必须设置状态核对截止时间、重试次数预算和升级处理路径，并在真实供应商验收之前确定。恢复手段耗尽后，即使上游结果仍然未知，也可以通过有审计记录的流程，将任务终结为“交付无法恢复”。这一终态应仅恢复一次积分，并包含适用的补偿积分，不得自动提交另一笔付费尝试。之后才到达的上游成功结果、事件或资产，应被隔离并交由运营管理员审核，不能重新打开任务，也不能再次扣减积分。积分预占不能以供应商最终成功完成状态核对为无限期前提。

### J5：购买和使用积分

Stripe 订阅按周期发放会到期的积分；一次性购买的积分包不过期。使用积分时，优先消耗最早到期的批次。账单事件必须经过身份校验、持久化保存、支持安全重放，并映射到具体工作区。余额应展示积分发放来源和到期时间。任务执行期间，即使原积分批次到期，已经预占的积分也不能因此丢失。

### J6：跨到期时间恢复积分

任务失败时，仍在有效期内的订阅积分分配额保留原到期时间，购买积分分配额仍然永久有效。已经到期的订阅积分部分，转换为一次性、七天有效的补偿积分。退还补偿积分时，保留该补偿积分原有的到期时间，不能重新开始另一个七天窗口。退还已经到期的补偿积分时，不得延长其有效期或重新变为可用积分。

### J7：管理团队与客户支持

在工作区范围内邀请、移除成员并管理账单。运营管理员可以检查用户、任务、资产、付款、配置健康状态、失败与成本记录、Webhook 处理结果及审计历史。恢复操作应调用与正常操作相同的领域服务；管理员不能通过直接编辑数据库表字段绕过积分余额或任务的不变规则。

### J8：使用联盟推广

交付一套完整、可选择启用的第三方联盟集成。每位买家使用自己的账号。默认只针对工作区的首笔有效付款计算佣金，无论该付款用于订阅还是购买积分包。续费和后续加购不得再次产生佣金。更换成员、付款人或账单客户映射关系，都不能重置返佣资格。由人工审核、运营者主动发起付款即可满足要求；自动打款属于可选能力。应用内生成积分的退还不等同于现金付款退款。

### J9：部署与更新

通过一条有文档说明的托管部署路径，或一条明确说明外部服务前提条件的 Docker 应用部署路径部署应用。Docker 部署承诺不意味着必须自托管 Trigger.dev 或全部外部服务。已购版本可以持续使用；购买包含十二个月的更新和基础支持。每次更新应说明版本、迁移要求、兼容性及对个性化修改的影响。

### J10：查阅并使用开发者文档

开发者访问模板销售网站的 docs 页面，了解模板及其支持的能力，按照对应发布版本的教程操作，使用文档说明的 Skills，并在扩展或集成自己持有的源码时查询 API／接口参考。文档覆盖模板使用、架构、配置、部署和升级；全部十二个初始 Skills 的用法、参数、输入／输出、保护边界和回退；以及实际支持的 API、内部接口、扩展契约和第三方集成。

API 参考内容必须从实际发布的契约生成，或与这些契约同步。必须明确标识内部接口和扩展点，不能将其描述为一套新增的公开 API 产品。D08 仍将公开生成 API 和客户 API 密钥管理延期；文档不得编造端点、授权方式或能力。

采用公开 Fumadocs／MDX Docs，提供目录、搜索、直达链接、发布版本导航和可复制示例。销售站 Docs 外壳不进入客户导出；买家必需指南随每次干净发布交付，并与网站使用同一版本化内容源。详细技术方案定义路由及发布／导出契约。

### 开源实现原则与已选后台边界

D31 确定优先采用持续维护、成熟、兼容且许可证允许目标源码交付的开源组件，减少通用能力自研。D22 要求 Shpitto 交付运营功能，不要求从零编写每个后台 UI 或 CMS 组件。D24 的第三方佣金引擎安排保持不变。复用不免除验证模板业务行为及其集成的责任。

运营后台选定 React-admin OSS 5.15.4，保留 Better Auth 会话与独立全局运营角色，以及 Drizzle 管理的数据表和迁移。Payload／Refine 是已记录备选，不是运行依赖。M0 验证所选配置、再分发权利、授权和导出；M1 集成。实际不兼容须以证据修订设计，不得悄悄更改 D15。本文不声称安装或集成完成。

| 领域 | 建议边界 |
| --- | --- |
| 后台 UI 与低风险内容 | React-admin 提供外壳、表单和列表。自定义 dataProvider 调用内部服务端接口；受保护配置变更走领域命令。 |
| 运营记录与操作 | 用户、工作区、订单、积分和任务采用自定义视图及服务端领域用例。不得为核心账本、任务状态、支付权益或权限开放直接可写的通用增删改查，包括框架自动提供的端点。所有特权操作保留服务端授权和审计记录。 |

## 6. 不可违背的产品规则

1. 每项私有操作都必须依据用户当前的工作区成员关系或明确的运营管理员角色进行授权。
2. 任务结算和积分变动必须在领域／数据库边界上具备幂等性，不受事件或消息重复投递的影响。
3. 供应商提交结果不明确，既不能证明成功，也不能证明失败；决定重试或退还生成积分之前必须先核对状态。
4. 供应商返回成功，但没有持久保存且可访问的输出，不算完成交付。
5. 积分来源、预占、到期和补偿来源链路，都必须能够从持久化记录中解释清楚。
6. 取消与派发必须通过同一个原子操作边界竞争，保证结果一致。
7. UI 修改不能悄悄禁用用于验证该修改的检查，不能创建替代支付路径，也不能把真实行为替换为 Mock。
8. 客户源码导出必须使用明确的允许清单和干净的 Git 历史；仅依赖忽略规则是不够的。
9. 必需检查失败时，必须阻止模板提供的受控发布流程。验证策略和工具来自候选修改差异之外、固定版本的可信基线；通过检查的验证记录必须将验证器版本与必需检查项，绑定到待发布源码、锁文件、契约及相关配置的内容摘要。导出／部署必须拒绝缺失、过期或不匹配的验证记录。买家仍然可以修改自己的源码或环境，因此不承诺绝对防篡改。
10. 初次运行包含持久化数据的核心演示，不需要云服务凭据；生产环境不能意外使用演示计费或演示任务驱动。
11. 已发布的开发者文档和交付给买家的必需文档副本，必须描述同一版本中实际支持的契约。销售站外壳仍排除在客户发布包之外；API 文档不得悄悄扩大 D08 的产品边界。
12. 采用的开源后台底座不能通过通用数据操作绕过领域授权、任务／积分规则或审计。必须明确身份集成、迁移所有权和干净导出义务；框架本身成熟不构成 Shpitto 集成正确的验证记录。
