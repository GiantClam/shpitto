## 1. 证据规则

每项验收关卡都必须记录：提交或发布标识、环境、用例编号、预期结果、实际观察结果，以及已脱敏的证据路径。证据缺失、受阻或跳过，均不能判定为通过。报告中不得包含密钥、签名 URL、会话令牌及原始敏感载荷。

对于网站定制和客户版本发布，必须记录最终暂存待交付源码、锁文件、契约及相关配置的内容摘要，同时记录固定版本的可信验证器与策略，以及实际必需验证集的执行结果。验证器必须从候选变更集之外加载。修改前已有的未提交工作需要单独记录。模板支持的导出或部署工具必须将当前暂存内容的实际字节与这些证据进行比对；证据缺失、过期或不匹配时，必须拒绝继续。仅记录 Git 提交标识并不足够。验证策略的变更必须经过明确的工程审查，并有意识地重新设定验证基线。

- 本地领域测试和 Mock Provider 只能证明本地行为。
- 供应商契约测试夹具只能证明适配器行为，不能证明当前账号或模型的可用性。
- 真实供应商覆盖必须使用已认证的实际服务账号，完成全部四种“供应商 × 生成模式”组合，并将输出下载至持久存储。这些调用在执行前必须获得明确的预算和凭据授权。
- Stripe 测试模式的证据，不能证明生产账号具备相应资格，也不构成真实扣款授权。
- 联盟模拟事件不能证明所选服务商的活动配置确实执行了“工作区首笔付款”规则。在服务商支持的情况下，必须获得基于其真实服务的测试证据，并明确标注任何限制。
- 部署验证必须基于干净的导出副本执行，不能只在开发者工作目录中完成。
- 开发者文档的验证记录必须标明对应模板版本和内容来源。导航、直达链接、示例及 API／Skill 说明须与该发布版本的实际契约核对；写有 API 文档并不意味着已经提供延后实现的公开 API。
- 后台证据注明选定 React-admin 版本、适配器／声明、后端授权入口、Drizzle 迁移归属和事务边界。兼容性声明、界面展示或安装本身不能通过 D31；缺少集成证据仍须标记待解决。
- 破坏性故障注入必须使用新的、可丢弃的测试夹具。保留买家的真实工作目录及无关修改。

**下文所有命令名称和测试路径，都是拟实现的接口，并不表示当前已经存在可执行命令。** 执行负责人必须先建立受支持的命令及其对应关卡，才能声称某阶段已达到退出条件。

## 2. 验证层次

| 层次 | 覆盖范围 | 建议证据 |
| --- | --- | --- |
| 单元／领域 | 积分发放批次的分配与到期、补偿来源链、任务状态转换、模型校验、授权决策、联盟返佣资格 | 使用可控时钟的确定性测试；领域分支覆盖率和失败边界用例 |
| 集成 | 真实本地 PostgreSQL 事务、成员关系变更、Webhook 收件箱／发件箱、持久化任务、存储、重试与重启 | 包含数据库断言的事务及并发执行；不能用内存实现替代原子性证明 |
| 适配器契约 | Replicate／fal、Stripe、Trigger.dev、存储、邮件、联盟映射 | 有文档说明的成功、失败、重复、乱序、超时夹具，以及必要的外部服务验证 |
| 端到端（E2E） | 本地演示、测试模式下的订阅与积分包、团队、生成与下载、管理后台、联盟入口、个性化 | 包含断言的浏览器流程、路由检查，以及桌面端／移动端截图 |
| 打包／部署 | 旧项目排除、密钥／源码允许清单、干净历史、独立安装、托管与 Docker 路径 | 清点及导出清单、镜像构建上下文检查、全新运行日志及服务检查 |
| 开发者文档 | 销售网站 docs 的发现入口，模板／Skills／API 栏目，与版本匹配的教程和参考，以及同步的买家指南 | 导航和直达链接检查、十二个 Skill 与契约的对应核对、文档版本／来源记录、脱敏示例审查，以及导出指南检查 |
| 后台底座 | React-admin OSS、Better Auth 会话／全局角色适配、领域命令、Drizzle 迁移归属、原子事务及客户交付 | M0 已选配置验证、data/authProvider 审查、越权拒绝和故障注入、依赖／许可清单及导出／部署证据 |
| 可观测性／恢复 | 事件关联、停滞任务、提交结果不确定、资产缺失、交付失败、积分账本事件 | 脱敏的结构化记录及有文档说明的恢复演练 |

在编写受影响的生产行为之前，先规划实现阶段的测试。**本次规划任务不新增或运行应用测试。** 实施计划应以所负责的核心领域模块至少达到 **80% 分支覆盖率**为目标；涉及资金、隔离及状态机的强制场景，无论总体覆盖率是否达标，都必须通过。

## 3. 核心测试夹具设计

- 用户 A／B／C、工作区 W1／W2、所有者／成员关系，以及独立的运营管理员账号。
- 使用可控时钟的订阅积分批次、永久有效的购买积分批次、补偿积分批次，以及混合来源的积分预留。
- 可按脚本控制的 Mock Provider，覆盖排队、运行、成功、失败、延迟响应、提交结果不确定，以及重复／乱序回调。
- 本地 PostgreSQL 和本地对象／资产持久化；仅在进程内维护临时余额不能满足要求。
- Stripe 测试模式购买和 Webhook 重放夹具；外部联盟及供应商凭据与本地默认配置分开管理。
- 网站定制夹具，同时包含预先存在的无关修改，以及一次故意修改受保护核心的操作。
- 打包夹具，在交付允许清单之外放置被忽略的本地文件及无害的密钥标记，以证明排除有效，且不暴露真实密钥。
- 标明发布版本的开发者文档源，包含模板教程、全部十二个交付 Skill 的说明，以及适用的内部 API／集成示例；销售网站正文和源码包必需的买家指南从这份共同来源生成或选取，示例使用占位符，不包含真实密钥。
- 可丢弃 React-admin 夹具：客户／工作区所有者／运营角色使用 Better Auth 身份，覆盖撤权、直接后台接口访问、重复特权命令、Drizzle 迁移记录及领域／账本／审计故障注入。不包含 Payload 自动接口或第二个 CMS 数据库。

## 4. 专项场景

### 持久化、身份与授权

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| T01 | 获取全新代码副本，不配置云端密钥；初始化本地依赖，登录，生成 Mock 视频，然后重启应用 | 身份、工作区、任务、积分和资产状态均持久保存；输出仍然可访问 |
| T02 | W1 的成员向任务、历史、资产、下载、账单接口传入 W2 的标识 | 服务端拒绝访问，不泄露 W2 数据或签名 URL |
| T03 | 移除成员，但其原有会话仍处于活动状态 | 该成员后续对 W1 的请求被拒绝；客户端缓存不能作为授权依据 |
| T04 | 工作区所有者请求全局管理接口；运营管理员执行受支持的调整操作 | 所有者被拒绝；运营管理员操作通过授权，并记录操作者、原因及关联标识等审计信息 |
| T05 | 重放邀请、使用过期邀请，以及在个人／团队工作区之间切换 | 成员关系变更只发生一次；到期规则和工作区隔离保持有效 |

### 积分与生成生命周期

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| T06 | 两个同时提交的任务争用不足以支付两者的余额 | 成功预留的任务数量不超过余额实际可承担的数量；可用余额不为负数 |
| T07 | 混用不同到期时间的积分批次和永久有效的购买积分 | 优先消耗符合使用条件且最早到期的积分；分配记录保留来源链 |
| T08 | 订阅积分批次到期时，其中一部分已被任务预留 | 未预留部分到期失效；已预留部分按原任务结果处理，不能重复花费 |
| T09 | 同一提交、回调及结算被反复投递 | 按业务语义仅产生一个任务／尝试、一次预留，以及一次终态积分处理；重复事件可被观察和追踪 |
| T10 | 取消操作与派发抢占同时发生 | 边界结果只能有一个：派发前取消成功并释放积分，或派发抢占成功、取消被拒绝 |
| T11 | 供应商已收到提交，但网络响应丢失 | 持久记录结果不确定的尝试；不能盲目再次发起付费提交；使用可用的供应商证据或运营管理员操作进行核对处理 |
| T12 | 后台工作进程在积分预留、派发、收到回调或存储复制后停止 | 重启后从持久状态继续或核对处理，不重复消耗积分，也不丢失终态效果 |
| T13 | 供应商报告完成，但载荷表示失败或输出不可用 | 适配器检查真实结果；不能错误地把任务标记为已交付 |
| T14 | 供应商生成成功，但资产复制暂时失败，源 URL 即将过期 | 在有明确上限的策略下重试／核对存储；只有输出持久保存后才可判定成功；最终交付失败按 D20 处理 |
| T15 | 即使上游已收费，任务仍进入最终失败状态 | 向终端用户全额退还本次生成积分；供应商费用和失败信息单独保留，用于运营成本报告 |
| T16 | 失败任务曾分配 100 个已到期的订阅积分 | 只创建一次 100 积分补偿，到期时间严格为退还时刻之后七天 |
| T17 | 补偿积分再次被预留，并在原到期时间之前／之后被退还 | 保留原补偿到期时间；不能滚动延长，也不能建立新的补偿发放来源链 |
| T18 | 失败任务使用了已到期订阅积分、仍有效订阅积分和永久积分的混合来源 | 只有符合条件的已到期订阅部分获得补偿；其他分配部分保留原有条件 |
| T19 | 任务完成终态结算／退还之后，又收到迟到或冲突的供应商回调 | 领域逻辑不能悄悄再次扣除或退还积分；按有文档说明的终态策略记录冲突，以供核对处理 |
| T20 | 任务队列已进入终态，但供应商结果仍不确定 | 不能将队列完成／超时等同于供应商成功／失败；必须显示待核对处理状态 |

### 账单与联盟集成

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| T21 | Stripe 订阅付款和积分包购买 | 正确工作区只获得一次积分发放，数量、来源和周期与配置一致 |
| T22 | Webhook 重放、乱序投递和伪造签名 | 重放不造成重复效果；状态得到核对与一致化处理；伪造事件被拒绝且不发放积分 |
| T23 | 付款失败、取消订阅、续费，以及已配置的套餐切换 | 权益及积分发放遵循已写明的生命周期；仅凭页面回跳 URL 不能认定付款生效 |
| T24 | 同一订单触发多种 Stripe 事件类型 | 稳定的业务去重键阻止不同事件类型重复发放积分 |
| T25 | 工作区首笔付款之后续费及追加购买积分包 | FirstPromoter 的稳定工作区 UID 和原生单笔付款佣金上限保证默认只返首笔有效付款，首购积分包也符合条件。重复投递不产生重复佣金，应用不自建佣金账本 |
| T26 | 首笔付款后更换付款人／成员／Stripe 客户映射 | 向 FirstPromoter 发送相同的稳定工作区 UID；该工作区资格不重置。第二个工作区独立判断 |
| T27 | 两名被推荐成员及相互竞争的推荐来源 | 所选归因策略必须结果确定、过程有记录，并通过所选服务的实际配置加以证明 |
| T28 | 比较现金退款／争议与生成积分退还 | 现金事件遵循明确的佣金冲正规则；仅发生应用内积分退还时，不冲正现金佣金 |
| T29 | 联盟功能先禁用，再使用买家自己的账号配置启用 | 禁用时核心应用仍正常工作；推荐关系仅关联到所配置的独立联盟计划 |
| T30 | 运营管理员审核佣金并发起受支持的结算流程 | 可获取相关状态及平台入口引用；操作演示在可用时使用测试模式，不擅自发起真实打款 |
| T31 | 出现被禁止的自我推荐或可疑的批量创建工作区行为 | 执行选定策略，但不能悄悄改变 D26 中合法的工作区资格；按规定标记并审计 |

T27／T28／T31 采用详细技术方案中的归因、冲正和反滥用具体默认规则。M6 验收前对照 FirstPromoter 账号／活动配置验证；服务默认值不得悄悄覆盖 D25／D26。不得将不受支持的能力声称为已配置。

### 迁移、导出、部署与运维

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |

## 7. 可观测性与故障演练

为工作区、作业、供应商尝试、Webhook 事件、积分操作和发布版本输出结构化标识。记录状态转换、派发结果不确定、未解决任务的持续时间、资产导入失败、重复事件处理，以及审计中的操作者／原因。绝不能将估算的供应商成本标注为已核对确认的实际支出。

在发布演练中，使用可丢弃环境：在作业派发后中断它，重放其供应商／账单事件，暂时让对象存储失败，移除一名工作区成员，并触发一次失败的 UI 验证。运营管理员必须能够定位问题，并使用文档所列操作恢复，同时保持授权与积分账本的不变约束。告警阈值和服务等级目标（SLO）应在观察模型实际耗时后配置；缺失数据必须明确标为未知。
