# Shpitto：开源运营后台底座评估

日期：2026-09-27  
状态：技术选型已完成，V1 采用 React-admin 开源核心。本文保留候选比较与未采用方案的集成风险，作为决策依据；后续实施以详细技术方案为准。依赖安装、原型、应用测试及部署尚未执行。

配套文档：[需求记录](./2026-09-27-shpitto-restart-requirements.zh-CN.md)、[重启计划](./2026-09-27-shpitto-restart-plan.zh-CN.md)、[验收规格](./2026-09-27-shpitto-restart-test-spec.zh-CN.md)、[英文对应版本](./2026-09-27-shpitto-admin-foundation-assessment.md)、[审核入口](./2026-09-27-shpitto-review-index.zh-CN.md)。

## 1. 结论与建议

采用“开源优先”的实现原则，复用通用后台、认证、UI、文档和基础设施集成能力。受维护的依赖可以减少通用功能开发量；组合后的产品是否稳定，仍需本项目的集成和领域测试证明。

**决定：采用 React-admin 开源核心 5.15.4。** 复用现成运营界面，并保留 Better Auth 会话和领域服务。Refine 需要更多界面组合；Payload 的内容管理、身份及迁移职责超出当前需要。开发者文档采用 Fumadocs + MDX。M0 验证这些已选组件的兼容与边界，替代原先三方竞选。

这个建议属于结合项目需求作出的架构判断：D22 主要管理用户、工作区、账单、积分、生成任务及恢复；D15 已将客户身份交给 Better Auth、业务持久化交给 Drizzle；D30 要求有版本的开发者文档，本身不要求运行时 CMS。Payload 覆盖的范围更广，因此需要证明它带来的复用收益足以抵消额外集成和运维成本。

D22／D24 中“自行提供运营管理后台”，意味着负责交付运营能力，不要求从零编写通用表格、表单、导航、内容编辑和认证。D24 仍然将佣金记账和付款流程交给选定的第三方联盟服务。

[当前详细技术方案](./2026-09-27-shpitto-detailed-technical-design.zh-CN.md) 提供具体版本、路由、数据接口与部署步骤。下文含历史候选比较和条件性风险；这不表示 Payload 或 Refine 仍处于 V1 待选状态，也不要求为未采用方案实现额外原型。

## 2. 候选方案比较

| 候选方案 | 可复用的现有能力 | 项目仍需完成的工作 | 本项目适用情况 |
| --- | --- | --- | --- |
| React-admin 开源核心 | 资源列表、表单、筛选，以及数据／认证 provider 契约；官方 Next.js 方案将后台作为客户端应用运行。 | 领域 API 与数据适配、Better Auth 或运营身份适配、服务端授权，以及财务／任务专用操作。 | 主要希望复用现成业务 CRUD 界面时优先评估；核实 UI 库与客户端包的影响。 |
| Refine Core | 无预设界面的数据、认证、访问控制 provider，以及 React／Next.js 集成。 | 组合选定 UI、连接 provider、实现受保护领域命令及服务端检查。 | 保留模板自己的 UI 体系和交互控制更重要时比较；界面组合工作通常更多。 |
| Payload | 配置驱动的后台／CMS，包含自己的认证、数据库适配器、自动 API 和内容管理能力。 | 选定运营身份方案、隔离数据结构所有权、保护所有启用入口，并建立调用领域服务的业务管理视图。 | 存在较多内容运营需求时优势更明显；需衡量自定义页面及额外后端管理成本。 |

能力依据：[React-admin 数据适配](https://marmelab.com/react-admin/DataProviders.html)、[认证](https://marmelab.com/react-admin/Authentication.html)、[Next.js 集成](https://marmelab.com/react-admin/NextJs.html)；[Refine 概念](https://refine.dev/core/docs/guides-concepts/general-concepts/)、[Next.js 集成](https://refine.dev/core/docs/routing/integrations/next-js/)；[Payload 概览](https://payloadcms.com/docs/getting-started/what-is-payload)、[管理后台](https://payloadcms.com/docs/admin/overview)、[内容版本](https://payloadcms.com/docs/versions/overview)。

三者开源核心均采用 MIT 许可证，但这不代表所有插件、素材和企业模块都有相同授权及费用。进入付费源码模板前，核对选定版本的许可和再分发条件；不能假定购买一份企业订阅，就能向所有模板买家转售私有模块源码。本评估没有要求或选定任何企业模块。[Payload 许可证](https://github.com/payloadcms/payload/blob/main/LICENSE.md)、[React-admin 许可证](https://github.com/marmelab/react-admin/blob/master/LICENSE.md)、[Refine Core 许可证](https://refine.dev/core/docs/further-readings/license/)、[React-admin 企业条款](https://react-admin-ee.marmelab.com/MARMELAB_Services_Terms_2025_01_29.pdf)、[Refine 企业模块](https://refine.dev/core/docs/enterprise-edition/multitenancy/)。

## 3. 无论选哪种后台，都保留的架构边界

```text
客户应用 -> Better Auth -> 工作区授权 -> 领域查询／命令

选定后台 UI -> 已验证的运营身份 -> 运营权限检查
                               -> 领域查询／命令

领域命令 -> 一个明确所有者的数据库事务
            -> 业务状态 + 积分变化 + 业务审计 + 适用时的发件箱记录

可选 CMS -> 自己的内容／管理员记录及迁移
```

客户身份、成员关系、积分、账单、生成尝试和私有资产继续只有一套权威业务实现。后台负责界面，调用其他产品流程也使用的领域服务。框架在客户端隐藏按钮或页面，只控制展示；特权请求仍需服务端核对当前权限。

| 操作／数据 | 复用方式 | 项目必须保留的边界 |
| --- | --- | --- |
| 导航、列表、筛选、表单、分页 | 框架组件与数据适配器 | 适配经批准的查询结果，不直接暴露任意表或密钥。 |
| 公告、FAQ、营销文案和公共媒体 | 确有需要时使用结构化内容 CRUD | 与私有生成资产、Shpitto 销售方数据分开；不因此新增浏览器可视化建站器需求。 |
| 用户／工作区／订单／任务查询 | 通过领域查询形成只读视图 | 工作区与全局运营权限、敏感字段脱敏。 |
| 积分调整、任务恢复、账号／成员变更 | 自定义操作调用领域命令 | 可信操作者、原因、幂等、目标授权、当前状态及原子业务审计。 |
| 价格、积分规则、模型启停和保留期限 | 经过校验的配置命令 | 明确生效版本并审计；保留既有订单和任务快照。这些配置会影响业务。 |
| Stripe 权益和联盟状态 | 既有集成适配器及第三方记录引用 | 支付事件保持权威性，不能通过手工改状态授予付费权益，也不另建佣金账本。 |
| 供应商凭据 | 受控密钥配置 | 不能通过通用内容表单或 API 返回明文密钥。 |

积分账本、余额、预占、支付事件、任务尝试和任务终态，不提供通用写入／删除操作。管理员身份不能绕过业务不变规则。内容版本历史也不能替代具有明确操作者、不可任意改写的财务和运营审计。

## 4. 未采用 Payload 方案的集成风险记录

### 身份与权限

终端用户继续使用 Better Auth。运营侧可以选择独立 Payload 管理员集合，或经过验证的自定义认证策略；不能假设已有官方即插即用的 Better Auth 桥接。独立运营登录可能比同步全部客户账号更简单。两条路径都必须产生稳定、由服务端验证的运营身份，并支持角色和会话撤销。不能只凭相同邮箱映射管理员权限。Payload 官方提供管理员认证集合和自定义策略能力。[管理员认证](https://payloadcms.com/docs/admin/overview)、[自定义认证策略](https://payloadcms.com/docs/authentication/custom-strategies)。

Payload 的 Local API 默认跳过访问检查，自定义视图也需要显式保护。这些属于集成时必须处理的行为。代表用户执行的调用，需要传入适当的已验证用户上下文并设置 `overrideAccess: false`；确需特权的服务端作业，应走范围明确且经过审查的服务路径。自定义视图、操作、端点，以及每个启用的 REST／GraphQL 路由，都要分别验证。[Local API](https://payloadcms.com/docs/local-api/overview)、[自定义视图安全](https://payloadcms.com/docs/custom-components/custom-views)。

自动生成后台／CMS API，并不意味着推出公开生成 API 产品。保留 D08，避免与现有应用路由冲突，只开放经过明确授权的操作。隐藏界面入口不足以完成控制。

### 数据库与事务所有权

Payload 的 PostgreSQL 适配器内部使用 Drizzle，但数据结构也由 Payload 配置驱动。当前官方文档将 `schemaName` 标为实验性，开发环境默认开启 schema push。使用相同数据库引擎，不代表可以安全接管应用已有的表。[PostgreSQL 适配器](https://payloadcms.com/docs/database/postgres)。

建议的原型边界：在同一本地 PostgreSQL 实例中，为应用业务和 Payload 使用独立数据库，各自拥有迁移及受限数据库凭据。这会增加数据库配置、备份和升级工作，但不必新增云服务。只有在固定版本的适配器证明迁移隔离有效后，才考虑共享实例内 schema 等替代方式。受控迁移流程禁用自动 schema push；两套迁移工具不能修改对方的表。

业务变更、积分变化和权威业务审计，保持在领域层拥有的同一个事务内。不能假设 Payload 请求事务与另一条 Drizzle 连接上的事务会原子提交。可选 CMS 展示副本或通知通过可重试、幂等的发件箱同步，不决定积分退还是否成功。Payload 提供事务能力，但集成必须明确使用兼容的所有权边界。[Payload 事务](https://payloadcms.com/docs/database/transactions)。

### 交付与内容范围

若 Payload 被选为买家运营后台，经批准的集成代码、初始化、固定依赖和迁移说明，必须属于买家可独立运行的源码交付。本地运行不能依赖 Shpitto 托管的 CMS，也不能强制要求云账号。Shpitto 销售方实例及私有销售记录继续分开。

技术 Docs 和 Skills 继续关联具体源码发布版本。D30 优先使用已有的版本化正文来源。如果之后证明有必要通过 CMS 编写，则为销售站文档和交付指南生成明确的版本快照。编辑器中的内容修订，不自动等同于模板版本。不能为价格、运行配置或技术文档建立两份互相竞争的权威内容。

## 5. 整个模板的复用策略

| 领域 | 计划复用 | 项目承担的责任 |
| --- | --- | --- |
| Web 基础 | 已确认的 Next.js／React／TypeScript | 产品组合及受支持版本兼容。 |
| 身份认证 | Better Auth | 工作区／运营授权与账号生命周期集成。 |
| 持久化 | PostgreSQL、Drizzle | 数据结构所有权、领域事务、幂等和恢复。 |
| 管理后台 | 已选 React-admin OSS 5.15.4；M0 提供集成证据 | 领域查询／命令适配及访问边界。 |
| UI 与个性化 | 经评估的开源组件、选定的现有 Skills | 模板专用契约、安全修改与来源记录。 |
| 文档 | 已选 Fumadocs/MDX 与版本化正文 | 模板／Skill／API 示例准确，交付指南同步。 |
| 支付、任务、存储、邮件、模型 | 已确认服务及其官方受支持 SDK／适配器 | 标准化事件，保持积分、任务和授权规则；这些服务并非全部属于开源软件。 |
| 联盟计划 | 一家受支持第三方集成 | 工作区首笔付款资格与同步；第三方拥有佣金记账和付款流程。 |

优先使用正式发布的软件包和受支持扩展点，避免大范围维护上游分叉。仅在许可证和维护收益明确时复制经过审查的源码。记录上游版本、选定包、必要声明、维护责任和升级路径。项目热度、漂亮演示或上游测试通过，都不足以独立证明本产品稳定。

## 6. M0 已选方案集成验证与稳定性门槛

针对已选 React-admin 配置，使用以下任务与合成数据验证。记录版本、适配投入、依赖、身份／迁移边界、许可、构建与升级成本。不要求实现未采用方案的原型，也不虚构节省工时比例。

1. 通过有权限检查的领域查询，展示带筛选的工作区／任务列表。
2. 通过领域命令执行一次有审计记录的积分调整，重放请求并确认只生效一次。
3. 如果存在持续内容运营需求，编辑一项低风险内容；若没有，则明确记录 CMS 提供的实际复用价值有限。
4. 验证客户／成员被拒绝、管理员撤权生效、直接 API 调用，以及对应框架特有的访问路径。
5. 注入业务事务中途失败；适用时执行独立 CMS 迁移或同步失败，确认业务状态与审计保持一致。
6. 从干净导出初始化本地应用，并记录 Docker／托管部署、依赖、许可证及迁移顺序。

| 门槛 | 未来需要提供的证据 |
| --- | --- |
| T59 | 运营身份和全部启用的后台入口遵守当前权限及撤权规则。 |
| T60 | 每项数据结构只有一个迁移所有者；领域事务失败不会拆开业务变更与审计，适用时证明框架迁移隔离有效。 |
| T61 | 通用 CRUD 入口不能绕过积分、支付或任务命令；重复操作幂等且可追溯。 |
| T62 | 固定依赖／许可证、独立客户导出、无需云账号的本地初始化和受支持部署路径可复现。 |
| G31 | 开源选型记录证明净复用收益，并通过适用集成门槛，明确剩余限制。 |

M0 验证已选 React-admin 配置，M1 集成，M6 完成运营功能，M8 验证独立交付。主要精确版本已记录在详细技术方案；安装和运行证据属于后续工作。

稳定性验收重点放在选定配置、新适配代码和关键产品流程上，使用上游支持的能力。保留现有资金、隔离和任务恢复等必需场景。通过复用减少需要重新证明的新代码量，同时验证最终组合的产品行为。
