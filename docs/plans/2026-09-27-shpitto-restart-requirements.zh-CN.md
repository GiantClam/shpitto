## 产品界面范围

模板包含其自身的视频服务营销页面、定价、身份认证、仪表盘、生成界面、历史记录、资产详情、工作区设置、订阅与积分管理，以及基础运营管理界面。

Shpitto 销售网站介绍源码许可、更新、支持和演示，并提供 D30 要求的开发者文档，其客户是模板买家。该网站的价格、账号和订单，不得与视频应用内交付的订阅和积分系统混淆。

视频应用演示应运行实际发布的模板。源码许可销售工具和内部开发记录不属于客户模板交付内容。

## 管理后台与联盟补充要求

### 运营管理后台

建议的 V1 运营基线包括：

- 用户和工作区管理，包括成员与账号状态。
- 查看订阅、付款／订单和积分发放情况，并关联相关支付供应商记录。
- 可审计的积分调整，以及预占、结算、积分退还、到期和补偿对应的积分账本条目。
- 检查生成任务和资产，查看失败详情，并执行受控运营恢复操作。
- 查看供应商／模型可用性、配置健康状态；上游提供相关数据时，展示用量和成本。
- 查看 Webhook 处理历史和管理员操作日志。

运营管理员与工作区所有者、成员是不同角色。授予客户工作区所有者身份，不得同时授予全局管理权限。财务和运营调整必须保留审计记录；管理界面操作必须遵守任务和积分账本的不变规则。

### 开源优先交付与已选后台底座

D31 确认尽量建立于合适的成熟开源项目、减少通用能力不必要自研的原则。D22 的管理后台要求意味着自行交付运营能力，不要求从零实现整套后台 UI 或 CMS。D24 仍将佣金记账和打款交由选定的第三方联盟服务负责。复用开源不能替代对 Shpitto 自身授权、任务、积分、计费和集成行为的验证。

运营后台选定 React-admin OSS 5.15.4，使用 Better Auth 会话、独立全局运营角色，以及领域自有的 Drizzle 持久化。Payload 和 Refine 作为历史备选保留于[评估文档](./2026-09-27-shpitto-admin-foundation-assessment.zh-CN.md)，均不进入运行时。M0 验证该配置、再分发权利、集成成本、授权、迁移归属及导出；只有实际障碍才触发有记录的设计修订，不再开展未定的三方选型。[详细技术方案](./2026-09-27-shpitto-detailed-technical-design.zh-CN.md)负责实施细节。

建议的实现边界：

| 领域 | 建议职责与保护 |
| --- | --- |
| 后台展示与低风险内容 | React-admin OSS 提供外壳、表单、列表和允许的低风险配置操作；自定义 dataProvider 调用内部服务端接口，受保护行为变更走领域命令。 |
| 核心运营数据 | 用户、工作区、订单、积分和生成任务通过自定义视图及服务端领域用例提供操作。不得为核心积分账本、任务状态、支付权益或工作区授权开放直接可写的通用增删改查；框架端点也不能绕过同样的服务端授权和审计要求。 |
| 身份 | Better Auth 会话识别用户；单独授予的全局角色授权运营人员。React-admin authProvider 映射真实会话，每个后端命令重新检查当前权限。工作区所有者不获得全局权限。最小工作区／成员／邀请规则仍由领域管理；不选用 Better Auth organization 插件。 |
| 数据库与迁移 | Drizzle 统一管理认证表及应用表的受审查迁移序列。React-admin 不拥有数据表或迁移；不引入 Payload 数据库或竞争的 schema push 流程。 |
| 业务与交付隔离 | 买家 SaaS 数据与模板销售方的销售及运营数据隔离。仅导出买家的后台能力、必需配置和允许的依赖，并附上适用声明；排除销售方数据和凭据。 |
| 开发者文档 | 保留 D30 的版本化、同源文档及客户导出。选择后台框架不意味着自动把 Docs 改成运行时 CMS，也不新增必须使用的托管编辑服务。 |

### 已确认的联盟范围与实现边界

用户已确认，以下两套独立业务都需要联盟支持：

1. Shpitto 招募联盟推广者销售源码模板许可，并为这些销售支付佣金。
2. 模板买家使用交付的联盟功能，为自己运营的视频 SaaS 招募推广者，并对其服务中符合条件的交易支付佣金。

两者的账号、归因、佣金记录和打款保持独立。D04 中轻量模板销售的决定仍然适用：支持模板销售联盟，本身不要求自建交易市场。模板销售方专用的销售实现不进入客户源码发布包；可复用的视频服务联盟能力则属于交付模板的一部分。

D24 为 V1 选定第三方集成方式。模板必须为初期支持的一家服务提供集成代码、配置指导和启用／禁用行为。应用需要负责：在注册和结账过程中保留推荐归因，将被推荐的付款人与工作区账单关联，按照所选服务契约处理适用的订单与现金订单退款事件，并提供运营配置和联盟入口。应用拥有已封存的工作区归因及首付款证据，FirstPromoter 记录该归因，并按配置项目拥有佣金金额、余额及结算；模板不得自建平行的佣金资金账本。基础运营管理后台仍然属于应用自身范围。

D25 确认了视频 SaaS 的默认规则：仅首笔有效付款产生佣金，无论购买的是订阅还是积分包。该默认规则下，续费和后续购买不再产生佣金。这是供模板买家使用、可配置的推广计划默认值，并不是写死在代码中、强制所有买家业务遵循的限制；它也不决定独立的源码许可销售推广计划。

D26 将工作区作为首笔有效付款资格的稳定身份；成员、付款人或支付客户映射变化不得重置。D26 本身未决定归因及无效交易处理；当前 E05 工程默认值已明确：创建时封存创建者三十天内最后有效且验证的触点，只为原候选保留待核验状态，不允许后续成员／触点替换。现金冲正保留已消耗资格；佣金拒绝／冲正后争议胜诉须供应商权威人工修正和审计。

D27 设定结算基线：运营者审核佣金，再通过所选第三方服务支持的流程主动发起付款。模板展示必要入口和状态信息。可选的自动付款取决于服务能力、买家资格和配置；不要求每位买家都具备，也不属于 V1 必须通过的验收条件。

FirstPromoter V2 及 E05 归因／冲正控制为已选工程方案。审核跨会话持久化，每五分钟同步，批准／托管付款入口前六十秒内权威刷新；未解决冻结、未完成拒绝或过时账户检查点阻止交接。佣金比例、计提基数、账号支持的付款方式／最低额及经济结算周期仍为商业发布参数。现金佣金不同于应用内推荐积分奖励；没有用户确认的佣金比例或多级体系。

买家 SaaS 工程基线选定 FirstPromoter V2 API、稳定工作区 UID 和服务原生的单笔付款佣金上限。详细方案定义归因、转化、去重及冲正契约。Rewardful 和 Lemon Squeezy 引用保留此前研究记录，不再是买家 SaaS 的待选服务。模板源码销售保持独立；账号权限、打款开户、资金及费用需要发布验证。

模板买家使用自己的推广计划和账号，并承担相应服务费与打款费用。运营应用时，联盟配置是可选项；交付一套完整、受支持的集成仍是 V1 要求。集成必须保留无需云服务的本地核心演示体验。视频生成失败后退还应用内积分，并不自动等于原现金订单退款，也不能被误当作佣金冲正事件。

### 供详细规划落实的受控修改设计

D29 要求在复用设计和组件能力时，由项目拥有并制定修改规则。实施计划应将下列设计具体化；这些是落实已确认要求的建议机制，不表示保护措施已经存在：

| 修改类别 | 建议边界 |
| --- | --- |
| 品牌和展示层定制 | 使用声明的配置／内容／主题区域、批准的展示组件和允许的路由。保留真实数据、现有服务调用、路由保护及共享页面框架行为。 |
| 产品扩展 | 使用供应商、生成任务、计费配置或其他受支持扩展的专用 Skills。声明受影响接口和预期行为变化；保留领域不变规则，并提供适用的迁移与回归验证记录。 |
| 受保护核心变更 | 身份认证、工作区授权、支付 Webhook、积分账本、生成状态转换、数据库模式及验证／发布规则，不属于普通页面编辑范围。需要这些变更的请求，必须重新归类为明确的工程变更，并拥有独立范围、影响评估和验证计划。 |

项目指导、产品契约和已授权的任务范围，决定如何适配引入的 Skills。引入示例不得悄悄增加替代计费流程、用 Mock 替换真实集成、删除工作区检查，或削弱验证规则，让定制看起来已经成功。通用设计示例属于输入材料，不是扩大任务范围的授权。

建议支持的工作流如下：

1. 检查当前模板版本、契约、配置、相关源码和已有未提交工作。
2. 对所请求变更进行分类，记录预期修改文件、受影响路由／接口、需要保留的业务行为和可恢复基线。常规且在范围内的修改不应要求用户反复确认。
3. 在声明的修改范围内组合批准的设计／组件资源。优先使用现有扩展点和共享组件；真正涉及业务变化时重新分类，不能悄悄将其当作视觉修改。
4. 对照声明范围检查实际差异，并校验配置、导入、类型和构建兼容性。未来验证计划应包含适当的 UI 和关键业务回归验证记录；仅凭文件允许清单不能证明语义正确。
5. 必需检查失败时，必须阻止任务被认定为成功完成，也必须阻止模板提供的、以验证为门槛的发布／部署流程。不得自动禁用检查、覆盖预期结果，或在缺少验证记录时宣称成功。
6. 输出变更报告，包含受影响文件、验证结果、剩余限制和有针对性的回退路径。保留用户预先存在或重叠的工作；不能把全面 hard reset 或替换整个项目作为自动恢复方式。

Skill 指令用于指导 Agent，并不是文件系统权限边界。源码模板让买家掌握自己的代码和环境，因此保护措施无法保证买家不能手动修改受保护代码或绕过本地检查。计划应结合架构边界、结构化配置、差异检查和可执行检查，并准确说明哪些受支持流程会强制执行这些检查。这不意味着需要许可证服务器或必须由供应商托管的编辑器。

## 已确认的跨到期边界积分退还行为

D21 明确了以下场景中 D12 与 D20 的配合方式：

- 某任务在订阅积分即将到期前，预占了 100 个有效订阅积分。
- 任务运行期间，订阅积分周期结束。
- 之后任务失败，没有交付可用视频。

用户获得从积分退还时起七天有效的 100 个补偿积分。这些积分与永久有效的购买积分分别记录，并展示来源和到期时间。如果这些补偿积分被另一个任务预占，而该任务也失败，再次退还积分时应保留已有补偿到期时间，不能再开启一个七天周期。

只有在失败任务执行期间到期的订阅积分部分，适用这一例外。退回尚未到期的订阅积分批次时，保留原有效期；购买积分仍保持不过期。实施计划必须保留积分批次的来源链路，避免通过重试产生持续滚动延期。
