## 2. RALPLAN-DR 决策摘要

### 原则

1. 交付由买家拥有、服务账号可独立配置的单一产品。
2. 在重试、个性化修改和运维恢复过程中，保持资金、积分及租户隔离规则成立。
3. 首次本地体验应具有真实的持久化流程，且不要求云服务凭据。
4. 在兼容性、许可证和维护净收益得到证明时，优先复用成熟开源能力；明确复用边界及来源记录，解除对旧平台的依赖。
5. 以可观察的结果作为发布依据；迁移可回退，导出边界明确。

### 三项主要决策因素

| 决策因素 | 对计划的影响 |
| --- | --- |
| 产品是可维护的源码产品，而非托管建站平台 | 应用位于仓库根目录；划分领域模块；通过外部编码 Agent 执行 Skills；客户仓库使用干净历史。 |
| 付费异步视频任务存在结果不确定性，也会产生真实上游成本 | 持久化提交尝试，核对不确定结果，按积分发放批次预留额度，保证业务效果幂等，并向运营者提供可见信息。 |
| 买家必须能够快速定制，同时避免破坏模板 | 声明可定制区域，由项目维护修改契约，检查实际差异，并设置业务回归验收条件。 |

### 可行架构方案

| 方案 | 优点 | 成本与风险 | 决策 |
| --- | --- | --- | --- |
| A. 根目录 Next.js 模块化单体，使用明确的领域模块和外部生产服务 | 符合已确认技术栈；交付一个源码产品；本地与生产共用领域服务；运维负担较低。 | 需要严格遵守模块导入和事务规则；长任务仍需要独立的工作进程运行环境。 | 选定为实施方向。 |
| B. 根目录 Web 应用，另行部署 API、积分账本及任务服务 | 进程隔离强，可独立扩容；适合团队规模或交易负载确有需要时采用。 | 增加买家的部署、认证、追踪、版本管理及本地配置负担；当前需求并不要求这些独立服务。 | 延后；保留适配器边界，允许未来拆分。 |
| C. 提取旧图片模板，全面重构后放入新根目录 | 现有认证、支付和界面模式可能减少初期工作。 | 可能无意继承旧假设、许可问题、依赖及平台输出契约；视频能力和新积分账本保证仍需补齐。 | 仅复用经过审查的选定源码；不将“提取旧模板”本身作为架构。 |

继续在原平台中原地改造，会保留用户明确选择冻结的运行时，因此不是同等满足要求的替代方案。应用支持 Docker 部署，并不要求替换 Trigger.dev，也不要求所有生产服务完全自托管。

### 三种上线失败预演

| 假设上线后发生的失败 | 早期信号 | 预防措施与验证记录 | 负责方向 |
| --- | --- | --- | --- |
| 供应商超时时，买家遭遇重复扣费或积分丢失 | 将结果未知的提交作为新任务重试；只维护可变余额；回调标识无法关联。 | 提交尝试与发件箱模型；再次提交前先核对；唯一结算键；Beta 前覆盖竞争、崩溃、事件重放及过期场景。 | 领域与集成方向。 |
| 页面修改 Skill 声称视觉修改成功，却破坏付费生成 | 界面将真实服务调用换成本地 Mock；扩大修改范围；关闭检查；仅审核截图。 | 契约和受保护路径；修改前后差异清单；独立验证；不安全定制反例；检查失败阻止发布。 | Skills、界面及评审方向。 |
| 归档或客户导出泄露私有状态，或仍依赖旧代码 | 使用宽泛复制或通配规则；清单遗漏被忽略文档；从开发历史克隆客户 Git 仓库。 | 明确清单和文件白名单；不复制原仓库历史；单独保全密钥；在独立干净环境安装、构建并扫描导出内容。 | 发布方向与独立评审者。 |

## 4. 目标仓库结构与应用边界

采用一个位于根目录的应用，内部按内聚的领域模块组织。除非迁移后仍有得到证实的需求，否则不引入 monorepo 任务框架。

```text
/
  AGENTS.md, README.md, package.json, pnpm-lock.yaml
  .env.example, .gitignore, next.config.*, tsconfig.json
  src/
    app/(marketing)/, (auth)/, (app)/, (admin)/, api/
    modules/identity/, workspaces/, credits/, generation/
    modules/assets/, billing/, affiliates/, operations/
    adapters/providers/replicate/, fal/, mock/
    adapters/tasks/trigger/, local/
    adapters/storage/s3/, local/, mail/resend/, smtp/
    components/ui/, marketing/, product/
    config/brand.*, navigation.*, plans.*, capabilities.*
    content/, styles/, db/schema/, db/migrations/
  trigger/                     生产任务入口
  skills/<skill-name>/          随产品交付的外部 Agent 工作流
  .shpitto/contracts/           路由、定制、业务及导出契约
  scripts/                     配置、验证、清点及导出工具
  tests/unit/, integration/, e2e/, contracts/
  docs/                        带版本的开发者内容；选定买家指南随版本导出
  deploy/                      Docker 与选定的托管部署方案
  vendor/                      源码许可销售及文档展示外壳；不导出
  internal/                    工程记录；不导出
  legacy/shpitto-platform/      冻结的旧源码；不参与运行或导出
  .git/                        原开发历史，保留在根目录
```

以上文件分组是设计目标，不代表路径已经存在。按实际需要创建目录，不添加通用插件框架、佣金引擎或重复的业务服务层。

| 边界 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 应用路由与 Actions | 校验后的输入、会话、工作区上下文、展示及响应组织。 | 供应商 SDK 规则、直接进行积分运算、直接跨工作区访问数据库。 |
| 领域模块 | 状态迁移、权限、账本命令、必须保持成立的业务规则。 | React 组件、任务运行时 SDK、供应商专属请求结构。 |
| 适配器 | 供应商、任务、存储、邮件及支付集成，输出标准化结果。 | 自行决定余额、积分退还或现金退款规则，另设一套授权规则。 |
| 数据库 | 持久状态、唯一性、事务和迁移。 | 保证远程系统的事件投递。 |
| Skills、契约与脚本 | 支持的修改规则、验证及发布记录。 | 让运行中的应用依赖编码 Agent，或阻止所有人工源码修改。 |

对密钥和特权服务实行仅服务端可访问的边界。路由组只负责组织代码，不承担授权；授权在服务端用例中执行。领域接口应小而明确，仅在外部集成边界设置适配器。

运营展示层选定 React-admin 开源核心，通过 Better Auth 会话适配和领域查询／命令接口工作。Drizzle 是唯一迁移和事务所有者。详细技术方案明确文件、依赖、权限及初始化方式。

## 5. 迁移、保全与回退

### M0：首次移动前的清点

记录每项内容的相对路径、分类、已跟踪或被忽略状态、必要的大小及哈希、目标位置、保全方式和原因。密钥仅收集文件名及元数据，绝不收集值。清点 Git 状态、未跟踪文件、被忽略文件、运行中的进程、已配置的本地部署状态、根目录脚本，以及对旧代码的导入。

| 分类 | 计划处理方式 |
| --- | --- |
| 已跟踪的旧源码与配置 | 根据明确清单移动至 `legacy/shpitto-platform/`；包括 `apps/web`、旧 workers、`packages/db`、`packages/schema`、`builder`、`sites`、已跟踪快照及声明文件。 |
| `.git` 与仓库历史 | 保留在根目录；不重新初始化、不改写历史，也不复制到旧项目归档。 |
| 当前被忽略的需求、计划及验证记录 | 大范围移动文档之前，将经过核对的 UTF-8 成果复制到明确纳入版本跟踪的内部文档位置；核对完成前保留原件。 |
| `.env*`、凭据、本地数据库和有意义的运行状态 | 通过安全的本地备份及映射保全，继续保持忽略；不得将值写入清单、提交或客户导出。 |
| `.codex`、`.agents`、`.omx`、编辑器及 Agent 状态 | 逐项分类；保留会话和用户状态，单独归档旧产品指导，有意识地替换根目录产品指令。 |
| `.vercel`、Cloudflare 绑定及部署引用 | 私下清点，不可不加区分地移动或修改；分别记录线上服务和本地映射。 |
| 依赖、缓存及生成产物 | 自动生成的依赖或构建缓存不是源码保全要求。即使位于名称含 cache 的目录，也要保留已跟踪快照、人工编写内容、必要记录和用户数据；默认不删除。 |
| 根目录笔记及临时目录树 | 对 `plan.md`、`task_plan*`、发现与进度笔记、`apps/.tmp` 等逐项分类，保留用户工作及相关记录。 |
| 新产品及客户文档 | 明确跟踪需要的文件；迁移时将宽泛的 docs 忽略规则改为有针对性的规则。私有记录不进入导出。 |

### 安全移动顺序

1. 建立执行分支，对照当前工作树审核准确的迁移清单。
2. 记录源码基线和私有保全清单；纳入 Git 无法恢复的本地修改及被忽略的人工文档。
3. 检查源路径和目标路径的绝对位置确实位于指定工作目录内；拒绝路径冲突、意外符号链接，以及将目录递归移动到自身子目录。
4. 按已审核清单使用原生 PowerShell 的字面路径操作；分成小批次进行可逆移动，保持 `.git` 原位。
5. 将历史根目录 `AGENTS.md` 与旧源码一起保留；围绕视频模板和受规范约束的定制编写新的根目录契约。
6. 替换根目录包、包工作区、检查及部署的通配规则，使 `legacy/**` 不参与安装、格式化、lint、类型检查、测试、打包、镜像构建上下文或导出。
7. 对比移动后的清单及哈希，检查生效中的导入与配置，逐项确认必要文件去向。
8. 在干净的检出或导出环境验证新根目录；不要求旧项目能够安装、编译或运行。

不能将 `node_modules` 移入归档并意外使其成为发布输入。隔离旧工具后，通过新的安装重新生成根目录依赖树。新应用不能隐式复用旧环境变量。

执行迁移前，以只读方式检查已配置的托管构建根目录、分支设置、钩子和服务依赖。证据检查阶段没有发现本地或已跟踪的 `.github` 工作流，但这不证明不存在外部自动化。无法获取的托管端信息应记录为待决策依赖。

在新应用开发前回退，使用逆向迁移清单及已保全的源码基线。实施后回退，则先单独保全新工作，再从记录的基线恢复已跟踪源码，并从私有保全位置恢复被忽略文件。不得整体重置或删除无关用户修改。线上服务退役需要单独决策，不能作为归档操作的隐含结果。

| 资产 | 输入上传、持久输出、对象键、归属、元数据及保留状态；每次访问都必须基于工作区授权。 |
| 计费 | 工作区计费账号、供应商客户映射、订阅、订单、发票及付款引用、Webhook 收件箱、积分发放周期键。 |
| 联盟返利 | 本地推荐元数据，以及工作区归因和资格引用；第三方标识及同步状态，不建立第二套佣金账本。 |
| 运维 | 管理操作审计记录、Webhook 处理结果、脱敏诊断、配置健康状态及供应商成本记录。 |

跨任务、积分预留和发件箱记录的操作使用数据库事务。通过唯一约束确保每个业务键只产生一次效果。积分使用整数单位，货币金额明确使用最小货币单位；不能混淆供应商收取的货币费用和终端用户的积分单位。

### 工作区与授权

- 注册账号时创建个人工作区；支持通过邀请组建 owner/member 团队，共享账单、任务、积分和资产。
- 在服务端用例及存储下载授权中检查成员身份和角色；不能信任浏览器提供的工作区 ID。
- 已选 E01 默认值：个人工作区仅有不可变的创建者所有者，不邀请成员、不转移所有权、不转换类型；另建团队后，成员可生成和读取，所有者管理成员与账单。团队转移对象须为已有活跃且已验证成员，并发变更不能移除最后所有者。E02 单独定义禁用用户、封禁工作区与账单冻结。
- 移除成员或暂停账号后撤销访问，包括新的签名下载请求；在存储契约中明确已经签发的短期 URL 如何处理。
- 运营管理员使用显式全局角色；租户所有者身份不意味着全局管理权限。敏感管理操作必须审计原因、操作者、目标及结果。

### 任务生命周期与提交

```text
queued -> dispatching -> submitted -> running -> materializing -> succeeded
queued -> cancelled
dispatching/submitted/running/materializing -> failed（已判定交付失败）
dispatching -> submission_unknown -> reconciliation -> submitted | failed
submission_unknown -> failed（有界恢复已耗尽；上游结果仍可能未知）
```

供应商适配器将不同上游状态归一化为领域事件；终态迁移必须保持单向，不得被后续事件回退。供应商返回成功并不足够：只有输出已持久保存、可用，并存在经过授权的资产记录时，任务才能进入 `succeeded`。

创建任务时，以原子操作预留报价对应积分并将派发写入队列。派发前取消与派发操作竞争同一条记录或版本，只能有一方成功。派发一旦取得该提交尝试的处理权，界面便不再提供取消。本地和生产驱动共用这一规则。

网络提交之前先持久化提交尝试。请求可能已经提交后发生超时，应进入结果未知状态，而非自动重试或退还积分。保留请求身份及可获得的上游标识，通过供应商支持的 API 和运营记录核对。不能假设上游支持幂等提交。仅对安全的查询、文件接收以及已知尚未提交的尝试进行重试，并明确各供应商的可重试条件。

不能因结果不确定而无限期占用客户积分。M4 前，必须为每个支持的模型确定有限的结果核对期限、查询及文件接收重试额度、升级处理节点，以及负责的运营人员。根据已核实的供应商行为、成本和输出限制设置这些值，并写入模型契约，不能凭空设定一个通用时长。期限从原始提交尝试开始持久记录，工作进程重试或人工重新分配不得重置。

区分上游执行结果和客户交付结果。当有界恢复策略耗尽，仍未交付可用资产时，以原子操作记录可审计的终态交付失败，并且仅一次全额恢复预留积分；必要时按照 D21 处理补偿来源链。供应商结果或成本仍可能未知，应由运营者在核对记录中跟进，不能因此无限延长客户积分预留。这种处理绝不能自动创建另一次付费提交。

任务进入终态交付失败后，迟到的回调及资产必须隔离，交由运营调查。它们可以更新上游诊断或成本记录，但不能重新打开客户任务、重新扣减已退还积分、附加一笔新的收费交付，或延长补偿有效期。发布验收必须覆盖恢复期限耗尽后供应商才返回成功的场景，详见 T53。

Webhook 与轮询通过同一个幂等状态迁移函数处理。供应商支持时校验签名；按适用要求校验时间戳和事件身份；必要时读取供应商权威状态。重复或乱序事件不能覆盖已有成功或失败终态。限制输入及输出 URL、MIME 类型、文件大小和获取目标地址，防止不安全的资产接收。

### 积分与失败补偿

1. 持久化积分发放批次，记录来源、原始来源、剩余数量和到期时间；购买的积分批次不设到期时间。
2. 按最早到期顺序预留可用积分，再按确定性的创建时间及 ID 排序。通过锁定或原子分配防止并发超额消费。
3. 预留期间保留每笔积分批次分配；周期到期使未占用积分失去可用性，但不能抹去任务执行中的分配记录。
4. 持久交付成功后仅确认一次消费；判定失败时，通过一个幂等操作释放或退还全部预留积分。
5. 尚未到期的订阅积分退回时保留原到期时间；购买积分退回后仍不设到期时间。
6. 失败任务中已经到期的订阅积分，转换为一次补偿批次，自第一次实际生效的退还操作起七天到期。
7. 补偿积分再次退还时保留该补偿批次的原始到期时间，即使该时间已经过去也一样；不得重新计时。
8. 派发前取消释放原分配；不能将 D21 的失败补偿例外隐式扩展到普通取消。
9. 即使用户得到全额积分退还，也要单独记录运营者承担的供应商成本。对结果的主观不满意按支持政策处理。

积分账本是审计历史；派生余额必须能够与发放批次、预留及终态操作核对一致。到期及管理员纠正通过追加记录体现，不删除历史。管理调整不能修改过去的条目，也不能绕过来源链限制。

### 计费

Stripe 结账及 Webhook 调用计费用例。以经过验证的服务端事件为依据，不能信任浏览器成功跳转。既要对收到的事件去重，也要对底层发票、付款和积分发放业务标识去重，因为不同事件可能描述同一笔付款。

周期积分使用规范已付发票行／服务周期键和该行原始周期结束时间，永久积分包使用规范确认付款键。已选 E04 基线为月度单一订阅价格，不支持年度、多项目订阅、预约换套餐或按比例计费。周期末取消保留已发积分；旧订阅终结且通过结账保护后才可新购。商品变化只影响未来购买或明确评审的迁移。状态、试用、未完成付款不发积分，同一权益不能被发票重复发为初始与续费积分。

付费订单退款或争议，与生成失败的积分恢复分开处理。对于订单退款时已经被消费的积分，必须选定明确政策；不能意外产生负余额，也不能撤销其他批次。货币调整和积分调整分别保存各自来源引用。

无需云账号的演示使用 Docker PostgreSQL、真实的本地认证和工作区、仅开发环境启用的持久任务驱动、结果确定的 Mock Provider 固定样本，以及通过相同资产接口访问的本地存储。建议使用本地邮件接收器记录开发环境邀请和密码重置链接，无需外部投递。不承诺额外的生产队列或自托管任务系统。

本地驱动领取已持久化的发件箱任务，进程重启后可恢复，并能够演示成功、失败、派发前取消和过期补偿。Mock 输出必须是真实可播放、且来源允许再分发的样本文件，不能使用失效 URL。必须显式标明演示模式，并拒绝将其作为生产配置。

生产环境的 S3 兼容存储应及时接收供应商输出，并提供经过工作区授权的下载。临时上游 URL 不能充当持久资产库。发布前明确超时、重试与退避、输出校验、存储失败处理、清理及保留策略。

已选映射：每个工作区一个当前 Stripe 客户，保留全部历史映射。首次销售导出前等待五分钟，完整核对历史映射下已付款，以 (paid_at,payment_id) 排序而非事件到达顺序。按工作区串行持久化首笔有效付款身份，后续成员、付款人或客户映射变化不重置。导出后发现更早已验证付款，建立持久冲突冻结与修复工单。

已选 FirstPromoter V2 服务端 Tracking API 使用稳定工作区 UID 和规范付款／退款 ID，关闭重复的原生 Stripe 销售跟踪。配置原生 By count=1 与本地 first_payment；非首付款佣金先冻结并拒绝，完成前不批准或进入付款。切换 provider_campaign 需匹配经评审的供应商配置。M0/M6 验证契约；不兼容须记录设计修订，不能静默放宽 D25–D26 或另建佣金账本。

已选 E05 归因使用创建者在创建工作区前三十天内最后有效触点，以签名 Secure/HttpOnly 第一方令牌保存并核验当前供应商／项目。创建时封存该来源；丢弃无效或过期引用，临时核验失败仅保留原候选等待核对。后续触点或成员不能替换。现金冲正按唯一增量关联原销售，不重置首次资格。佣金已拒绝／冲正后争议胜诉须保持人工修正冻结，直至供应商权威修复与审计完成；生成退积分不冲正现金佣金。

运营者通过第三方支持的流程审核佣金并发起付款。如果正式支持的流程位于第三方管理界面，V1 可链接过去，但必须记录准确的交接步骤和状态可见范围。明确区分佣金追踪与实际打款，并说明费用、资金准备、地区及账号资格要求。默认验证不包含真实资金转账。

Shpitto 源码销售选定 Lemon Squeezy 托管结账及独立联盟计划，以每买家独立干净 GitHub 私有仓库和版本 ZIP 交付；供应商数据、账号与源码权益不进入买家 SaaS。

### 开源优先的后台基础（D31）

运营后台选定 React-admin 开源核心，复用业务列表、表单、筛选及管理外壳。开发者 Docs 选定 Fumadocs 与版本化 MDX。Refine 需要更多界面组装；Payload 额外引入 CMS、身份及数据结构管理职责，而 V1 没有足够的内容工作流需求。评估文档保留这些取舍依据。M0 验证已选方案的集成，不再开展开放式框架竞选。

共同边界不变：Better Auth 负责客户身份，服务端领域服务授权工作区和运营操作，Drizzle 管理的事务保证账本、计费、任务及审计规则。合理复用列表、筛选、表单和导航，但业务视图必须经过领域查询，特权修改必须经过明确授权的领域命令。基于数据适配器的界面候选，并不天然需要第二套身份存储或迁移所有者。

## 9. 受规范约束的定制与开源复用

### 修改分类与可执行边界

| 分类 | 允许修改的区域 | 必需控制 |
| --- | --- | --- |
| 品牌与展示 | `src/config/brand.*`、内容、主题变量、允许修改的组件及路由。 | 配置结构检查、实际变更文件范围、响应式与无障碍验证记录、现有 Action 和数据契约。 |
| 产品扩展 | 专门的供应商、任务、积分、资产及部署扩展点。 | 明确接口变更，必要时提供迁移，并给出针对性的领域和集成验证记录。 |
| 受保护核心 | 认证、授权、Webhook、积分账本、任务状态机、数据结构、验证及发布策略。 | 重新分类为明确的工程变更，声明影响并接受独立验证。 |

维护机器可读契约，涵盖可编辑配置、必需路由和 Actions、受保护模块、业务断言、扩展点及交付白名单。项目维护的 Skills 在这些契约内组合上游资源。上游示例不能覆盖本次任务的修改范围，也不能隐式安装依赖。

支持的工作流：检查版本和已有修改；分类修改范围；记录预期文件、路由及不可破坏的规则；建立基线；执行编辑；比较包含新增和删除文件的实际差异；运行必需检查；预览有代表性的状态；输出变更、验证记录及回退摘要。如果目标跨越原边界，必须重新分类。

将初始未提交修改和未跟踪文件，与拟执行的个性化差异分别记录。它们是要保全的用户工作，不能被视为可信策略更新，也不能自动免除最终验证。恢复只撤销本工作流产生的修改，避免整体 reset 或 checkout。保留可逆编辑记录或限定范围的补丁，同时避免暴露密钥。验证失败时，结果仍为未完成，并阻止模板支持的发布命令。

验证策略、必需测试集合定义和验证工具，应从候选修改集合之外的、固定版本的可信模板发布基线加载，例如经核验的只读参考副本。使用前检查版本和内容摘要。候选版本对脚本、契约、锁文件或配置的修改，不能重新定义必需检查，也不能自行批准。改变该可信基线必须进入明确的工程变更范围，经过独立评审并记录新的基线；普通个性化操作不能完成这种提升。

验证记录必须绑定到最终暂存源码的内容摘要、锁文件、适用契约、相关非敏感构建及部署配置、可信验证工具与策略版本、必需测试集合 ID 及结果。导出或部署前立即重新计算摘要；记录缺失、不完整、过期或不匹配时，阻止支持的操作。验证后任何源码或配置修改，都必须重新执行受影响的检查并生成记录。最终导出暂存目录须独立验证，避免文件筛选或转换后仍沿用另一棵目录树的记录。

采用模块导入边界检查、路由和 Action 契约检查、配置结构校验、类型及构建检查，并覆盖有针对性的资金、积分和租户隔离回归场景。包括修改越界、检查损坏、验证工具或策略被篡改时拒绝通过（T54），以及验证后源码变化时拒绝复用结果（T55）。视觉记录补充功能检查，不能替代功能检查。

这些机制保护的是产品支持的工具流程。买家拥有源码，可以人工修改或绕过，因此不能宣传为无法破坏的编辑沙箱。V1 不包含内嵌浏览器可视化编辑器。

### 执行人员安排：最多四个并发 Agent

| 名额 | 职责与限制 |
| --- | --- |
| 负责人／集成者 | 负责需求、共享数据结构及契约、集成顺序、评审决策及最终验收。 |

| --- | --- |

## 15. 架构决策记录

**决策：** 构建根目录 Next.js 模块化单体，以工作区归属的领域服务、生产任务及供应商适配器、持久化本地演示驱动，以及受契约约束的外部 Agent Skills 为核心。冻结旧平台，将新产品导出到拥有干净历史的客户仓库。

**决策因素：** 独立部署；正确处理异步资金和积分；可复现的首次体验；受保护的定制；可维护的付费源码分发。

**选择原因：** 方案 A 满足已确认的根目录产品和部署范围，同时保留唯一权威的工作区、积分账本和任务规则。其适配器边界同时支持本地演示和生产服务，无需引入旧平台运行时，也无需买家运营一整套新的微服务。

**考虑过的替代方案：** 独立 API 或微服务；全面重构旧图片模板；继续保留当前建站平台作为运行时。前两种方案包含有价值的提取或复用思路，但当前会增加不必要的范围或继承风险；最后一种与冻结旧项目的方向冲突。

**支持提取旧代码的最强反方论点及综合结论：** 方案 C 保留已经可用的认证、结账、界面和部署代码，可能更快交付；重写也可能丢失生产中已经积累的行为。因此，方案 A 不要求重写每个模块：当许可证、领域契约及回归记录证明复用有价值时，可以有选择地提取经过审查且兼容的源码。保留其有效行为和测试，替换旧平台耦合及未经证实的假设。代价是明确投入提取审查工作；接受这一成本，以同时避免整体继承和无必要的重复实现。

**后果：** 一个可部署应用更便于买家使用，但必须落实模块边界和事务纪律。本地驱动增加一个小型开发适配器，通过领域契约检查与生产行为的一致性。买家拥有的源码依然可编辑；受支持的 Skills 和发布工具提供保护，而非绝对锁定。

详细技术方案已确定技术栈、后台、Docs、部署、供应商端点与联盟适配器。M0 针对这些选择记录兼容性与账号证据。商业价格、许可条款和付费验证预算保留为明确的发布输入。验证失败需要有依据的方案修订，不得暗中改变 D01–D31。
